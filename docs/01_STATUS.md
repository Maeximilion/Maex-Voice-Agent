**The order travels in the conversation state (T-2.4, the cart, 07.10.2026), so a real model keeps it across turns.** A model gets the compact state and one input per request and keeps nothing itself; until now a dish found in one turn was gone in the next, and a pickup order over several turns could not work on a real model. Now the model writes the whole order as `cart` in its answer, in the form of `items` of `draft_order`, and the state sends it back with every turn. **What the core decides (`agent/guards.py` `take_cart`, `agent/state.py`):** a cart is taken whole or not at all, and only when every line names a dish from a clear match of `search_menu` or a candidate the guest was asked about by name (rule 2); a refused cart stops the whole answer, neither its sentence nor its tool call is carried out, and the model gets a hint. Number, name and the mandatory options still open (`open`) are added to a line by the state from the search result; a name or a price a model writes there is dropped, and no price goes into the state at all (rule 1). A cart that differs from the order that was read back, or one that was refused, drops the draft that waits for its yes, an order or a reservation, so a later yes cannot confirm what the guest just changed or a table the conversation has left (rule 3); a successful `draft_order` makes its items the cart, a confirmed order empties it. A `cart` left blank (`null`, `""`, `{}`) says nothing; a list is the order, also the empty one, so a guest can remove the last dish and the draft that held it is gone (both from the Codex review of PR #237, P1x2: in the first version `[]` counted as "unchanged" and a reservation that was read back survived a changed cart). Second round of that review (P1, P2x2), fixed: `false` or `0` as `cart` is refused instead of read as blank; a dish that was sold out at its search does not get into the cart; and the same order in another sequence of lines or options, or with an option in another spelling (third round, P2), is no change, so a model that repeats the order the other way round with its `confirm` does not cost a second readback. **The rules for the cart go out only in a call about an order.** The answer format has two versions (`agent/llm.py`): the short one of before, and `ORDER_FORMAT` with the field `cart`, its rules, the names of the slots (the model wrote `customer_name` and lost the name) and the sentence that a cart is no order yet (the model called `confirm` on its cart). The client sends the long one only while the state carries `cart`, which it does from the first menu search of a call on. A call about a table sends what it sent before: about 2,240 estimated tokens, an order call about 2,430 of 2,600. **Also new, in every call:** on tool hops the state lists the tools already called in the turn (`called`), because the model asked `get_service_status` again on its own result until the hop limit. **Taken out again:** a first version also showed the dishes a search had found that were not in the order yet; on the real model the candidate the guest had not chosen stayed in sight and was ordered two turns later, so only the order goes back to the model. **Measured (local llama-server, `qwen3.6-35b-a3b`, invented cases only; the model answers the same prompt the same way, two identical runs gave identical results):**

| What the model gets | Reservation cases (6) | Pickup cases (14) |
|---|---|---|
| as on `main`: short format, no cart | 6 passed | 0 passed, 10 ended with the team |
| as built: cart in the state, its rules after the first menu search, `called` | 6 passed | 1 passed, 6 ended with the team |
| cart rules in every request (tried, not kept) | 1 to 3 passed over three variants | 0 to 5 passed over five variants |

So the cart costs the reservations nothing and moves pickup from 0 to 1 of 14: the state now carries the order, and in the replays the model drafts the right order from it turns later (`abholung_0002`, `abholung_0003`), but that is not what keeps this model from finishing a pickup call. It loses the thread: it greets and asks the service status again in later turns, drafts before it has a name, calls `confirm` without a draft, and copies an order id wrongly on the final yes. Every addition to the prompt of a reservation call cost cases (4 of 6 with the slot names, 3 with the cart text, 1 with both), which is why a table call gets none of it. In each pickup run up to three more cases were right in the database and red only because the model tried a `confirm` the core refused. Three gaps the runs showed (invented name and phone number, the eval counting refused calls as hard violations, the guest's wish not kept across turns) are in "Open Points from Reviews" and are the start of part 4.

**The conversation core holds hard rules 1 to 3 itself (issue #216, 06.10.2026), a precondition for wiring a real model.** Until now only the scripted stand-in and test doubles drove the loop, and both follow the rules by construction; the system prompt asks a real model to follow them, which is no enforcement. A refused call goes back to the model as a failed tool result with a `hint`, stands in `calls.tool_calls` and costs one tool hop, so a model that insists ends in the handoff. Also from that review (P2): the call time limit is read again when the model has answered, a late answer is neither spoken nor dispatched. **Card numbers with a prefix and the ending g (T-4.12, 26.09.2026): the Sushi and sauce numbers from the register are understood.** T-4.11 dropped 50 dishes because search and import only knew a number up to 999 plus a to f. The register has `S1` to `S53` and `SM1` to `SM6` (Sushi) and `25G` to `60G` (sauces). Which prefixes exist is not in the code: `numberwords.CardFormat` reads them from the active numbers of the card (`items.card_format`, hard rule 1), and a one-word category whose numbers all carry a prefix becomes a spoken word for it. So "S zwölf", "Es zwölf", "S 12", "SM eins", "Es Em eins" find S12 and SM1, "Sushi zwölf" looks up S12 and SM12 and takes the one on the card, "Sushi eins" asks "S1 oder SM1?". The ending g works like a ("fünfundzwanzig G", "25 g"). Never a guess: "S 13" is not dish 13 and "Nummer 23g" is not 23, both are `not_found` when the card lacks them. The import accepts `s12`, `sm1`, `25g` (duplicates by `canonical_card`, `S7` equals `S07`), the tablet sorts S2 before S12 and finds "S1" in its search field. ## Versioning of This File

Own, semantic version `MAJOR.MINOR.PATCH`, independent of the `CLAUDE.md` bundle version and of README gate version (`docs/15_README_STRATEGY.md`) — README versions the product outward, this file versions itself inward:

| Bump | Trigger | Example |
|---|---|---|
| **MAJOR** | Gate passed / stage transition / architecture decision (E-Nr) flipped | G0 passed → stage 1 begins |
| **MINOR** | Decision made (D-Nr answered), new work package result changes "What's next" | D1 vendor chosen |
| **PATCH** | pure status housekeeping: task check, new assumption, new/resolved blocker | T-0.1 to done |

**Auto-update:** `python scripts/status_bump.py <patch|minor|major> "<one-line change>"` sets date, version, and changelog line automatically. Called by `/done`, `/task`, `/handover` (see `.claude/commands/`) — by hand only if needed. Extra safety net: CI (`.github/workflows/ci.yml`) fails if `docs/07_WORKPACKAGES.md` changes but `docs/01_STATUS.md` stays unchanged in the same diff.
