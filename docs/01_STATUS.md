## Summary

CI enhancement (17.09.2026): The `docker-smoke` job builds the API image without local CA certificate and starts it without bind mount. It checks `/health`, rejection of missing/incorrect tokens, and an authenticated ping. This automatically catches earlier Dockerfile errors with certificate and package path. The test checks container startup, not DB integration; that stays in the pytest suite. Local Docker execution was not available in this session; execution via GitHub Actions.

The plan is set (`docs/00_PCF.md`, v1.0, released). The repo is set up and contains a **runnable minimal skeleton**: FastAPI with `/health`, token auth, response envelope, JSON logging, DB session, and the ten stage-1 tables per Alembic migration 001 with an idempotent seed with test configuration; hot-path tools (`get_service_status`, `check_slot`, `create_reservation`, `confirm`, `transfer_to_team`) respond in roughly 8–15 ms (p95); 295 tests passing. Reservation is complete: `create_reservation` creates the draft with `readback`, `confirm` makes it valid, writes `audit_log` and places the `reservation.confirmed` event in the outbox. The dispatcher (`api/events/`) empties the outbox: its own process, one POST per event to n8n with event id as idempotency key, backoff 5 s / 30 s / 2 min / 10 min, then `failed` with alarm in log. Callbacks are also done: `create_callback` creates the task for the team, logs it, and reports it via outbox. `transfer_to_team` hands escalations to the team: always the extension from `service_config.team_phone`, never a main number, and runs at most once per call (state on `calls.transfer_reason`). The call log is done: `POST /v1/calls/start`/`/end` open and close the `calls` row the rest of Stage 1 depends on, and every `/v1/tools/*` call now lands in `calls.tool_calls` with duration and result, written generically by `core/tool_log.py` so no individual tool needed to change. `prompts/system_v1.md` and `tools_v1.md` are also done, scoped to the six tools that actually exist today.

`agent/` now exists (T-2.1, 17.09.2026): `prompt.py` loads `prompts/system_vN.md` and can append a menu index once one exists; `state.py` is the compact per-call state from docs/05 §5 (`stage`, `intent`, `slots`, `open`) instead of a growing transcript; `dispatch.py` is the direct, non-HTTP equivalent of `api/tools/*.py` — validates arguments, calls `domain/` straight (no HTTP detour, per docs/11 §agent), auto-derives `idempotency_key` for `create_reservation`/`confirm` so the model never has to (CLAUDE.md §2 rule 1), and writes every call into `calls.tool_calls` itself since the HTTP middleware never runs on this path; `loop.py` drives customer-turn → model → tool-calls → reply, aborting cleanly on `max_call_seconds` or a runaway tool loop; `llm.py` defines the swappable `LLMClient` interface plus a `FakeLLM` test double — a real model with token counting is T-2.4. **Codex review PR #101 (P1×3, P2×2) fixed same-day:** `LLMTurn` gained an optional `state_patch` so conversational details the model extracts (name, date, party size, ...) survive into the next compact state instead of vanishing the moment the turn ends; `state.to_prompt_json()` now exposes `reservation_id` once a draft exists, so a stateless model can still supply `entity_id` to `confirm` on the customer's "yes"; the loop rechecks `max_call_seconds` before every tool hop, not only once at turn start; a tool's `say` is now forwarded to the model instead of dropped, so it isn't left to invent wording for cases the code already has a prescribed sentence for; and — the one that mattered most — hitting `max_call_seconds` or the tool-hop limit no longer just *announces* a handoff to the team and hangs up: it now actually calls `transfer_to_team`, falling back to `create_callback` when a phone number is known and the team is unavailable, and only falling back further to the plain apology when neither is possible (CLAUDE.md §2 rule 5).

**T-2.2 done (17.09.2026):** `agent/ladder.py` is the understanding ladder as a small state machine (docs/05 §2) — per-field failure counts (`UnderstandingLadder`), one level-up after two failed attempts at the same information, and `should_end_call()` once three level-ups pass without success; stages 4 (keypad) and 5 (SMS) are context-specific tools per docs/05 §2, not mandatory rungs, so Stage 1's reservation fields (date, party size, name, phone) only ever climb through 1–3 before the ladder gives up on its own. `agent/escalation.py` is the immediate-trigger check from docs/05 §4 (complaint, human-requested, cancellation) — plain keyword matching on the raw customer text, run in `loop.py` before the model is ever called, so an obvious case costs no tokens. Both are wired into `loop.py`: `LLMTurn` gained `understanding_failure` (the field name that failed) so the model only has to report failures, never count them; a ladder hint (`{"field": level}`) rides along in the compact prompt state once a field is elevated; escalation runs first in every `run_turn()`, ahead of even the `max_call_seconds` check; and every loop-internal handoff (timeout, hop limit, ladder exhaustion, or a genuine escalation trigger) now goes through the same `_handoff()` from the T-2.1 Codex fix, just with the real reason threaded through instead of a hardcoded placeholder. **Codex review PR #102 (P2×3) fixed same-day:** a repeated `understanding_failure` for the same field within one `run_turn()` call (e.g. reported once on a tool-call hop and again on the final reply) now counts once, not once per hop, so the ladder can't climb faster than the customer actually failed; `escalation.py`'s cancellation trigger now matches the noun "Storno" itself (`"storn"`), not only the verb forms; and `_handoff()` now threads the triggering customer text into the `create_callback` summary, since a pre-model escalation never calls the LLM and would otherwise leave the team a fixed phrase with no record of what the customer actually wanted. Still open: the GUI.

**T-2.3 done (17.09.2026): the through-cut without a phone runs.** `sim/` is the text phone: `python -m sim.cli` holds a call in the terminal, `python -m sim.replay <case>.json` replays a transcript in the format from docs/08 §1, and both write to the real database — a confirmed reservation is in `reservations` afterwards, without any voice platform. `sim/session.py` holds what both entry points share: `start_call` opens the `calls` row, the compact state runs through `agent/loop.py`, every tool call is shown with the duration that `calls.tool_calls` recorded, and `end_call` derives the outcome from the conversation state (`confirmed` to `completed`, `transferred`, `callback`, otherwise `abandoned`) instead of from what the model claims. `sim/noise.py` garbles input on purpose — letter swaps, cut-off and swallowed words — with a seed, so a failure of the understanding ladder is reproducible instead of anecdotal. Because a real model only arrives with T-2.4, `sim/scripted_llm.py` stands in for it: rule-based, scoped to the reservation flow of `prompts/system_v1.md` (status, collect, `check_slot`, `create_reservation`, read back, confirm on a clear yes). It recognizes party size, day and time, name and phone number; what it does not recognize it reports as a failed attempt to the ladder rather than guessing (CLAUDE.md §2 rule 2), and a failed tool without a prescribed sentence makes it really hand over instead of announcing it (rule 5). Measured on the first case (`evals/cases/reservierung_0001_tisch_fuer_vier.json`): four customer turns, tool calls between 7 and 15 ms, reservation `confirmed` in the database. **Codex review PR #104 (P1x4, P2x2) fixed same-day:** a yes is now matched at word boundaries, so "Im Januar muss ich erst nachsehen" no longer counts as the explicit yes that turns a draft into a booking (CLAUDE.md §2 rule 3); an out-of-scope request (menu, pickup, delivery, allergy) is checked before the status call and remembered until the callback exists, because the follow-up turn usually carries nothing but the phone number and would otherwise drop the caller back into the reservation questions; a reply naming only a new time ("dann halb acht" to an offered alternative) keeps the day already given instead of rebooking the evening onto today; an impossible spoken date ("am 31.02.") counts as not understood rather than being silently replaced by today, and no longer escapes the conversation loop as a ValueError; and `finish()` closes the call at the current time instead of the start time, so a conversation from the terminal no longer records zero seconds (`--now` still pins the clock for a reproducible replay); and a correction during the read-back ("Nein, wir sind fuenf Personen") now builds a new draft with a new read-back instead of leaving the old one in place, where a later yes would have confirmed the four-person draft the customer had just corrected. The corrected-away draft stays in the database as a draft and blocks capacity until the cleanup job for abandoned drafts exists (already listed as missing above). 46 new tests, 341 in total.

## Made Assumptions (subject to change)

- Python 3.12, FastAPI, PostgreSQL 16, Alembic, pytest, ruff
- GUI as FastAPI + Jinja2 + HTMX + SSE, one container, no Node build
- One location (<Pilotbetrieb>), but multi-tenant schema: each location-related table carries `tenant_id`
- German as the only language in stages 1–6
- Payment at pickup or delivery, no phone payment
- **Operations day begins at 05:00 local time** (`api/core/time.py`, `DAY_STARTS_AT`): an order at 00:30 counts toward yesterday. Not defined in any document, assumption from 16.09.2026, subject to change
- Domain logic errors respond with HTTP 200 in envelope so voice platform presents them to agent; only missing auth is 401
- **Test configuration in seed is placeholder** (`scripts/seed.py`): Monday closed, 11:30–14:00 and 17:00–22:00 for all services, capacity 30 (midday) / 40 (evening) guests in 30-minute slots, wait time 20/45 min. Real values come with C1 and then replace the seed
- Seed never overwrites `service_config`: live switch (mode, delivery, wait time) belongs to team
- **Capacity without dwell** (`domain/reservations/capacity.py`): `capacity.max_guests` is the sum of all guests whose reservation begins in the slot; slots represent seat turns (e.g., 18–20 and 20–22 hours). Drafts count, cancelled and soft-deleted don't. `check_slot` additionally requires an open `dinein` slot (special days override). Alternatives only same day, in `slot_minutes` grid, two next closest to request, never in the past. Not defined in any document, assumption from 16.09.2026, subject to change
- Open drafts block capacity until confirmed or cancelled; a cleanup job for abandoned drafts is still missing (candidate for `jobs/`)
- **`create_reservation` requires a known call** (`domain/reservations/create.py`): the `calls` row must exist before the first write, else `not_found` with outage `say`. No silent creation, so wrong IDs from platform surface immediately. Since T-1.9 (17.09.2026), `POST /v1/calls/start` is how that row gets created; before that it had to be created by hand or in tests. Assumption from 16.09.2026, subject to change
- **Draft checks the slot again** by the same rules as `check_slot`; booked → `conflict` with alternatives in `say`. Idempotency replay doesn't check again and returns the stored response; same key under a different tenant → `conflict`
- **Check and create are locked** (`_lock_business_day`): an advisory lock per tenant and day (`pg_advisory_xact_lock`) holds to transaction end, else two simultaneous calls read the same free capacity and overbook the slot. Coarse enough for phone load, fine enough that different days don't block each other. Same pattern used later by `confirm`
- **Readback format** (`domain/reservations/spoken.py`): "A table for four people today / tomorrow / on Tuesday the 22nd of September at half past six under the name Müller[, with the note: …]. Does that work?" Party size up to twelve as word, above that digit. Reference point for "today" and "tomorrow" is `created_at` of the draft, not current time, so a replay after midnight delivers the same sentence. Wording is suggestion, to be refined in dialog test (D4)
- **Phone numbers** are normalized to E.164 format in `domain/customers/phone.py`, default country `+49`; `0049…`, `0…`, spaces, slashes, and parentheses are resolved. Suppressed number not yet modeled (comes with `find_customer`)
- Each write writes `audit_log` (`actor: agent`, `action: reservation.draft_created` or `reservation.confirmed`), inline in domain code. Two places don't justify a shared helper yet; check again at three
- **`confirm` is idempotent over state, not key** (`domain/confirm.py`): a second call reads `confirmed` and responds the same way, even with different `idempotency_key`; a second outbox event never occurs. The key only goes in `audit_log`. This saves a separate key table; if later a transaction can exit `confirmed` state, this assumption flips. Assumption from 17.09.2026, subject to change
- **`confirm` requires the same call as the draft** (`domain/confirm.py`): `reservation.call_id` must match the calling `call_id`, else `not_found`. Otherwise one caller confirms the table of another guest, and the "yes" from rule 3 comes from the wrong person. Today this doesn't break anything because the draft UUID only comes from `create_reservation` of that same call. A later "guest calls back and confirms" would be its own path with its own check. Codex review PR #90 (P1), 17.09.2026
- **Simultaneous `confirm` calls are serialized per row lock** (`SELECT … FOR UPDATE` on the reservation), else two calls write two events to outbox and kitchen gets the transaction twice
- **`entity: "order"` is in contract but responds `not_found` until stage 2**: the branch in `domain/confirm.py` is where T-4.x adds the order. `pickup_code` stays `null` for reservations
- **`approved` (overflow operation) deliberately missing:** `RESERVATION_STATUSES` knows only `draft`, `confirmed`, `cancelled`. Approval flow comes with T-8.2
- **Backoff sequence and retry count** (`api/events/dispatcher.py`): 5 s, 30 s, 2 min, 10 min per docs/03, then `failed`. That's five delivery attempts total; `attempts` counts every attempt, including the successful one. Assumption from 17.09.2026, subject to change
- **Alarm is for now an ERROR line in log** (`dispatcher._on_failure`): no channel to team (phone, chat, GUI banner) yet. Once GUI is up, alarm goes there too. Assumption from 17.09.2026, subject to change
- **One event per transaction, fetched with `FOR UPDATE SKIP LOCKED`**: no event goes out twice even if two dispatchers run, and a slow HTTP call doesn't hold foreign rows. Order follows `next_attempt_at`, not arrival order
- **n8n treats event id as idempotency key** (header `X-Idempotency-Key`, docs/03 § outbox): a retried delivery after timeout must not create a second receipt in the kitchen. The workflow that handles this is still missing
- **Migrations no longer silence the app logger** (`db/migrations/env.py`): `fileConfig(..., disable_existing_loggers=False)`. Before, after the first migration in the same process every already-imported logger went silent, even in production after `alembic upgrade` from the same process
- **Lint rules live in `pyproject.toml`, not ruff default** (17.09.2026): without config, ruff version determines the rule set, and a Dependabot update fails red without code changes (PR #85, ruff 0.7 to 0.16: 14 violations). Set are `E, W, F, I, B, BLE, C4, UP, SIM, DTZ, RUF` without `E501` (formatter determines line length), plus `extend-immutable-calls` for `Depends` and friends because FastAPI needs the call in the default argument and B008 is not an error there. Verified with ruff 0.7.4 and 0.16.8, both green
- **Python stays 3.12, Dependabot jumps on the image are disabled** (17.09.2026): version lives in seven places (Dockerfile, CI, `pyproject.toml`, README badge and text, `CLAUDE.md`, this document, `CONTRIBUTING.md`); a PR that only bumps the Dockerfile (PR #82, 3.12 to 3.14) moves one and isn't tested by CI because CI doesn't build the image. 3.12 gets security updates through October 2028. The jump comes as its own work package when a dependency requires it or support end nears, moving all places together plus a `docker build` step in CI
- **`create_callback` is idempotent over state** (`domain/callbacks/create.py`): per call there's at most one open callback, a second call returns it. No `idempotency_key` in contract and no extra column; platform timeout must not leave the team two slips for the same guest. A completed callback (`done`) doesn't block a new one. **Check and create are per-call locked** (`pg_advisory_xact_lock`, like draft reservation): a lock on the callback row reaches for nothing because it doesn't exist yet. Contract: every future write path on `callbacks` takes the same lock, and database runs `READ COMMITTED` (set in `api/db.py` as of 17.09.2026 instead of server default) — under `REPEATABLE READ` the waiter doesn't see the foreign commit and creates a second one anyway. A second call does **not** update the existing callback: differing `summary`, `phone`, or `reason` are discarded. Codex review PR #95 (P1), red test first; plus a controlled overlap test (A holds lock, B waits and then reads A's callback) and a rollback test. No idempotency rule for this tool was set in docs/04, assumption from 17.09.2026, subject to change
- **The sim understands time by rule, not by model** (`sim/scripted_llm.py`): "halb acht" is 19:30, an hour below eleven means the evening ("um sieben" is 19:00), from eleven the number stands as said so the 11:30 lunch table does not become 23:30. A time without a day means today if it is still ahead, otherwise tomorrow. A day without a time is not enough for a reservation and counts as not understood. Assumption from 17.09.2026, subject to change and only relevant for the simulator — a real model (T-2.4) resolves this itself
- **The sim writes into the same database as the API** (`sim/session.py`): a call from the terminal is a normal `calls` row with normal tool calls, not a separate test path. That is the point of the through-cut, but it also means test conversations show up in the GUI and in reports later. A separate marker for simulated calls does not exist yet; candidate as soon as shadow measurement (stage 4) counts real calls. Assumption from 17.09.2026, subject to change
- **Read-back sentence after callback** (`SAY_NOTED`): "I've noted your number. The restaurant will call you back as soon as possible." Wording is suggestion, to be refined in dialog test (D4)
- **Bugfix in `normalize_phone` (17.09.2026):** a bracketed `(0)` after the country code was kept as digit, `+49 (0)7221 5551234` gave `+4907221 5551234` — a number that doesn't exist. Now it's dropped for international format and kept as leading zero for national. Found building T-1.7, red test first (`api/tests/test_domain_phone.py`)
- **E9 (set, 16.09.2026):** Everything runs on EU servers or with EU vendors, including transcription and analysis. Maxi's PC is only a development workbench.
- **`prompts/system_v1.md` covers Stage 1 only, not the full skeleton from docs/05 §1** (`prompts/system_v1.md`, `prompts/tools_v1.md`): docs/05's example skeleton includes a menu index and order-taking rules, but `search_menu`/`draft_order`/etc. don't exist until Stage 2 (T-4.x). Writing a prompt that references them would tell the model it can do something the code can't (CLAUDE.md §2 rule 1). Instead, unbuilt tools are named once as "not yet available" so the model routes those requests to `create_callback` (`reason: out_of_scope`) instead of guessing. `tools_v1.md` is a new file, not named in docs/05 — the task title asked for "tool descriptions for the platform" without specifying a format or filename, so it's versioned alongside the system prompt (`tools_vN.md`) rather than folded into `docs/04_API_TOOLS.md`, which stays the full contract (error codes, idempotency rules) and isn't meant to be handed to a model as-is. Token budget is checked with `len(text) / 4` as an approximation (~440 for v1 against an 800 budget) — a real tokenizer arrives with `evals/` (T-5.1); until then this is a rough but honest floor check, not the number a real model would report. Assumption from 17.09.2026, subject to change once D1 and `agent/prompt.py` (T-2.1) exist
- **`/v1/calls/start` and `/end` are our own contract** (`api/schemas/calls.py`, `domain/calls/`): docs/04 lists the two endpoints (§Endpunkte) but, unlike the `/v1/tools/*` tools, doesn't spec their request/response shape. Designed to match the existing conventions: `start` takes `tenant_id`/`external_session_id`/`caller_id`, is idempotent over `external_session_id` while a call with that id is still open (a platform retry gets back the same `call_id` instead of a second row); `end` takes the same `call_id`/`tenant_id` shape as the tool contracts plus `outcome`/`intent`/`cost_cents`/`model`, and is idempotent over state like `domain/confirm.py` (a second `/end`, e.g. a late "error" after an already-recorded "completed", reads back the first result instead of overwriting it). Both live directly in `main.py`, like `/health` and `/v1/tools/ping`, since they aren't part of the agent tool surface. Assumption from 17.09.2026, subject to change
- **`calls.delete_after` is 24 months from `started_at`** (`domain/calls/start.py`, `_delete_after`): docs/03 §Löschfristen names 24 months for anonymizing `calls` rows without personal fields, but doesn't say when that date is computed. Set once at call start rather than at `/end`, because the column is `NOT NULL` and a call must never sit without one. No cleanup job reads it yet (candidate for `jobs/`, docs/01 already lists a similar gap for abandoned reservation drafts). Assumption from 17.09.2026, subject to change
- **`caller_id` is normalized best-effort, never rejected** (`domain/calls/start.py`, `_caller_id`): a suppressed number stays `NULL`; anything else goes through `normalize_phone`, but if the platform's caller id isn't a phone number `normalize_phone` can parse, the raw value is kept as-is rather than failing the call. A call must never be lost over the log being imprecise (CLAUDE.md §2 rule 5). Assumption from 17.09.2026, subject to change
- **`calls.tool_calls` is written by a generic middleware, not by each tool** (`core/tool_log.py`): every `/v1/tools/*` response (except `ping`, which has no `call_id` and isn't a real tool) gets one entry `{name, duration_ms, ok, error_code?}` appended via an atomic `jsonb ||` update, keyed off the `call_id` in the request body. Best-effort: a broken `call_id` or a DB hiccup logs a warning and never changes the response the agent gets. Runs in the thread pool (`starlette.concurrency.run_in_threadpool`), not inline in the middleware's `async def`, so one slow write can't serialize concurrent tool calls on the event loop. Assumption from 17.09.2026, subject to change
- **`transfer_to_team` availability is derived from opening hours** (`domain/callbacks/transfer.py`): `available` is true whenever any service window (`dinein`/`pickup`/`delivery`) is currently open, false otherwise. There is no real reachability signal (a line ping on the extension) before the telephony adapter exists (T-1.11, after D1); this is the only fact in the DB today that says anything about someone being present. `available: false` doesn't fail the call — the agent falls back to `create_callback` per docs/05. Assumption from 17.09.2026, subject to change once the adapter can report a real answer/no-answer
- **`agent/dispatch.py` re-does what `api/tools/*.py` does over HTTP, directly** (T-2.1, docs/11 §agent: "`agent/` darf `domain/` benutzen, nie `tools/`"): validates arguments into the same Pydantic request schemas, calls the same `domain/` functions, and writes the same `calls.tool_calls` entry itself (via a new `core/tool_log.append_tool_call()`, factored out of the HTTP middleware so both paths share one SQL statement) — because that middleware only runs on the `/v1/tools/*` HTTP path and never sees calls the agent core makes directly. Assumption from 17.09.2026, subject to change
- **`agent/loop.py`'s `_handoff()` defaults to reason `"not_understood"` for a self-triggered handoff** (`max_call_seconds`, too many tool hops, or the understanding ladder giving up — T-2.2): closest existing fit for "the loop itself gave up" rather than a genuine customer request; `TransferReason`/`CallbackReason` (docs/03) have no dedicated value for it and adding one is a schema change out of scope here. Assumption from 17.09.2026, subject to change
- **`agent/escalation.py`'s trigger words are a first pass, not a linguistic study** (`docs/05 §4`): plain substring matching on lowercased text for the three Stage-1-relevant triggers (complaint, human-requested, cancellation) — deliberately narrow (misses paraphrases, synonyms, negation like "keine Beschwerde") to keep false positives low, since a false trigger here skips the model and the ladder entirely. Assumption from 17.09.2026, subject to change

## Versioning of This File

Own, semantic version `MAJOR.MINOR.PATCH`, independent of the `CLAUDE.md` bundle version and of README gate version (`docs/15_README_STRATEGY.md`) — README versions the product outward, this file versions itself inward:

| Bump | Trigger | Example |
|---|---|---|
| **MAJOR** | Gate passed / stage transition / architecture decision (E-Nr) flipped | G0 passed → stage 1 begins |
| **MINOR** | Decision made (D-Nr answered), new work package result changes "What's next" | D1 vendor chosen |
| **PATCH** | pure status housekeeping: task check, new assumption, new/resolved blocker | T-0.1 to done |

**Auto-update:** `python scripts/status_bump.py <patch|minor|major> "<one-line change>"` sets date, version, and changelog line automatically. Called by `/done`, `/task`, `/handover` (see `.claude/commands/`) — by hand only if needed. Extra safety net: CI (`.github/workflows/ci.yml`) fails if `docs/07_WORKPACKAGES.md` changes but `docs/01_STATUS.md` stays unchanged in the same diff.
