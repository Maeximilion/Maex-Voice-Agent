# 23 - Access design and threat model for several customers

> Issue #569, epic #567. Written 09.11.2026 before any of it is built. Builds on D32 (one Docker
> stack and database per customer, one shared Caddy, docs/13 §8). Decisions of Maxi are marked with
> their D number; everything else is the proposed design that #570 to #576 build against. Nothing in
> this document is live yet. The security audit of docs/09 §5 is due before the operator dashboard
> or a customer login becomes reachable from outside (trigger "a new public path behind Caddy").

Every token is one per stack, generated by hand into that stack's `.env`: `AGENT_API_TOKEN`,
`KITCHEN_BRIDGE_TOKEN`, `GUI_PROXY_SECRET`, `VOICE_MEDIA_TOKEN`, `MONITOR_PUSH_TOKEN`, the n8n
and push credentials, the database passwords. Outside dev and test the API refuses to start on a
placeholder, short or shared token (docs/13 §3). docs/06 §6 says "no user management, one shared
access per device, a PIN for the admin area"; #570 replaces that line once Maxi has chosen the
granularity of the login.

With D32 the tenant boundary is the stack boundary: a customer's rows live in a database no other
stack can reach (separate Compose project, separate `backend` network, separate role and password).
The new risk D32 brings is the parts that are shared on purpose: the host, the shared Caddy and the
operator dashboard.

## 2. Assets

| Asset | Why it matters |
|---|---|
| Guest data per customer (names, phone numbers, addresses, allergy notes, order history) | personal data, Art. 9 for allergies; a leak between customers is a data breach for both |
| Money and bookings (orders, reservations, remedies of D19, call mode) | a forged write costs a restaurant money or a table |
| The fate of a call (call mode, team telephone, outage path) | rule 5: a changed mode or number can silence a restaurant's line |
| Tokens and passwords of every stack | each opens one customer; the set of them opens all |
| The operator account | reaches every customer through the dashboard |
| The host (root, SSH key, Docker socket) | holds every stack, every `.env` and every backup |
| Menu uploads | a new customer's files, possibly with metadata (location in photos) |

## 3. Trust boundaries

```text
Internet
  │ 443
  ▼
shared Caddy (host) ──── one site per customer: <customer>.<domain>  → that stack's api (gui, kitchen, health)
  │                 └─── ops.<domain>                                → operator stack (dashboard)
  │
  ├── stack A: api, dispatcher, voice, asterisk, n8n, push, db   (own networks, own .env)
  ├── stack B: ...
  └── operator stack: dashboard + its own small database (operator accounts, its audit, stack registry)
         │
         └── one internal network per customer stack, "ops", holding only the dashboard and that stack's api
```

Boundaries, outermost first: internet to Caddy; Caddy to one stack; dashboard to one stack's API;
inside a stack the networks of docs/13 §3 (unchanged); host to everything.

## 4. Threats

Severity is the residual risk after the planned design: high needs a deliberate decision to accept,
medium is accepted with the named limit, low is noise.

| # | Threat | Path | Design answer (section) | Residual |
|---|---|---|---|---|
| T1 | Stolen operator login | phished or reused password, stolen laptop session | individual account, passkey plus TOTP second factor (D33), short sessions, step-up for dangerous actions, rate limit, new-device alert (§5) | medium: a stolen unlocked laptop with a live session works until the idle limit |
| T2 | One customer reads another's data | a session or token of A used against B; a misrouted Caddy site; a missing tenant filter | stack per customer (D32); every token is per stack and never shared; session bound to the stack's tenant and checked on every route; provisioning tests that each site reaches its own stack (§6, §8) | low |
| T3 | Upload abuse | a crafted image or PDF exploits the parser, a decompression bomb, a script served back to a browser | type by content, size and page limits, parsing only in a throwaway container without network, re-encoded copies only, never served, deleted after import (§9, D33) | low |
| T4 | Token leak | `.env` copied off the host, a token in a log, a screenshot, a lost register PC | per-stack tokens from provisioning, files mode 600, never printed or logged, rotation runbook per token (§7) | medium: a leaked token works until rotated; there is no automatic detection |
| T5 | Brute force | password guessing on a customer login or on the dashboard | per-account and per-address counters in the database, growing delay instead of a hard lock, generic error texts (§5, §6) | low |
| T6 | Supply chain | a poisoned package or image | hash-pinned requirements, pinned images, Dependabot, CodeQL (unchanged); new libraries only where named here (§10) | medium, as today |
| T7 | Host compromise | SSH key stolen, container escape | SSH keys only, `ufw`, unattended upgrades, no Docker socket in any container, non-root containers (docs/13 §3); backups encrypted | high, accepted: one host holds every customer (D3, D32). Reassess with the stack count (docs/13 §8) |
| T8 | Lost or stolen tablet | a kitchen tablet with a live session | long session per device, revocable from the customer's admin area and from the dashboard; no secret readable on the device beyond its session cookie (§6) | medium: the finder sees today's board until revoked |
| T9 | Cross-site request | a page in the tablet's browser posts to the view | existing CSRF double submit plus `HX-Request`, plus an `Origin` check on writes; `__Host-` cookies, `SameSite=Lax` (§6) | low |
| T10 | Pivot from a taken-over container | Asterisk or n8n reaches the API or another stack | networks of docs/13 §3 unchanged; the `ops` network holds only the dashboard and one api; Caddy is the only container on several stacks' networks and routes by host name only (§8) | low |
| T11 | Operator dashboard taken over | a bug in the dashboard, its session or its libraries | it holds every stack's ops token, so this equals T1. Limited by the ops API: no raw SQL, no bulk export, personal data only with a recorded reason, every write audited in the customer's own `audit_log` (§8) | medium |
| T12 | Silent change to the fate of a call | an operator or customer session switches the call mode or the team number | step-up re-authentication, audit entry with actor, a push to the `ops` topic and to the team on every change of mode or team number (§5, §8) | low |

## 5. Operator login and dashboard (#571)

**Where (D33, Maxi 09.11.2026): public, behind a strong login.** Its own host name `ops.<domain>`,
never a path on a customer's host. Caddy adds the security headers of the operations view (CSP
without inline script, `frame-ancestors 'none'`, HSTS, `nosniff`, `no-referrer`) and the 256 kB
body limit; uploads (§9) get their own, larger limit on their one route.

**Accounts:** one named account per person (today only Maxi), never a shared one. Stored in the
operator stack's own database, not in a customer's. Password hashed with `hashlib.scrypt`
(standard library, n=2^15, r=8, p=1, 16-byte salt), at least 12 characters, checked against a short
list of common passwords.

**Second factor (D33): passkey and TOTP.** A passkey (WebAuthn, `py_webauthn`) is the normal way in
and cannot be phished on a look-alike site. TOTP (RFC 6238, standard library HMAC, no new library)
is the backup. Ten single-use recovery codes, stored hashed, are the last way in. Rules:

- Login needs password and one second factor; there is no login with password alone, ever.
- At least two passkeys are registered before TOTP may be removed, so one lost device never locks
  the operator out.
- A new passkey, a new TOTP secret or a used recovery code needs a fresh second factor and sends a
  push to the `ops` topic ("new device"), so a silent takeover is visible.
- Break glass when every factor is lost: SSH to the host and a CLI command in the operator stack
  that resets the factors of one account. SSH is the real root anyway.

**Sessions:** server-side rows, cookie `__Host-ops_session` (`Secure`, `HttpOnly`,
`SameSite=Strict`, path `/`), random 32 bytes, only its hash stored. Idle limit 30 minutes, absolute
limit 12 hours, rotated at login. Step-up (a fresh passkey or TOTP within the last 5 minutes) before:
viewing personal data of a customer, rotating or showing a token, changing a call mode or team
number, creating or deleting a customer, changing operator factors.

**Brute force:** failed attempts counted per account and per client address in the operator
database (survives a restart; production runs one uvicorn worker, but memory would reset). From the
fifth failure a growing delay (1, 2, 4 ... up to 15 minutes) instead of a hard lock, so an attacker
cannot lock Maxi out for good. Error text is the same for unknown user, wrong password and wrong
factor. The client address comes from Caddy's `X-Forwarded-For`, trusted only from Caddy.

**Audit:** logins, failures, factor changes and every action in the dashboard go to the operator
database's own audit table (actor, action, target customer, time; no guest data). An action on a
customer is also written to that customer's `audit_log` with actor `operator:<account>` (§8).

**Dev tools behind the dashboard:** read-only in production: eval and measurement results, the log
of one call by `call_id`. The simulator console stays `ENV=dev` only, because a simulated call
writes real rows; a demo customer is a stack of its own with invented data.

## 6. Customer login (#570)

Built after Maxi chooses one login per restaurant or one per staff member (open in #570). The rules
below hold for either choice.

- **Replaces Basic-Auth** on the customer's site. `GUI_PROXY_SECRET` stays: it keeps requests from
  inside the Docker networks out of the view, independent of the login.
- **Accounts in the customer's own database**, each bound to the stack's `tenant_id`. Every GUI
  route takes the tenant from the session and checks it equals the stack's tenant; the session of
  one stack is not valid in another, because its row lives only in that stack's database. Kept even though D32 makes it redundant, so a later shared stack (docs/13 §8 "Reassess")
  does not start without the check.
- **Hash** `hashlib.scrypt` as in §5. A device PIN for the tablet (4 to 6 digits) is only a quick
  unlock of a session that already exists, never a login; five wrong PINs end the session.
- **Sessions per device:** `__Host-session`, `Secure`, `HttpOnly`, `SameSite=Lax`, server-side row,
  sliding 30 days on the tablet so a kitchen with wet hands is not asked to type a password every
  shift. Each device is listed in the customer's admin area with its last use and a "Gerät abmelden"
  button; the dashboard can end every session of a customer at once (lost tablet, T8).
- **Admin area** (opening hours, zones, call mode, team number): step-up by password or PIN within
  the last 15 minutes. A change of call mode or team number also pushes to the team and to `ops`
  (T12).
- **Password reset only by the operator:** the dashboard makes a one-time setup link, valid 24 hours,
  shown once; no e-mail flow, no security questions. The customer sets the password on first use.
- **Brute force** as in §5: counters in the customer's database, growing delay, generic error text.
- **CSRF** as today (docs/06 §9) plus a check that `Origin` (or `Sec-Fetch-Site: same-origin`) names
  the site on every write, and the login form carries its own CSRF token (login CSRF).
- **Second factor for customers:** not required at start; the tablet session is long and the admin
  area has step-up. Offered later as an option if a customer asks.

## 7. Secrets and tokens

| Token | Scope | Made by | Rotation trigger |
|---|---|---|---|
| `AGENT_API_TOKEN` | one stack, inside its networks | provisioning (#573) | suspected leak, offboarding |
| `KITCHEN_BRIDGE_TOKEN` | one stack, its print bridge | provisioning; entered on the customer's PC at installation (#574) | lost register PC, staff change at the register, leak (runbook docs/09 §2) |
| `GUI_PROXY_SECRET` | one stack and the shared Caddy's site for it | provisioning | leak |
| `VOICE_MEDIA_TOKEN` | one stack, Asterisk to `voice` | provisioning | leak |
| `MONITOR_PUSH_TOKEN`, n8n and push credentials | one stack | provisioning | leak |
| `OPS_TOKEN` (new) | one stack's ops API, held by the dashboard | provisioning | leak, dashboard compromise (then all of them) |
| database passwords | one stack | provisioning | leak |

Rules:

- **Every token is per stack, made by the provisioning script with `secrets.token_hex(32)`**, never
  typed, never reused between stacks or between two variables of one stack. The existing start
  checks (no placeholder, at least 32 characters, distinct from `AGENT_API_TOKEN`) extend to the new
  ones.
- **Files:** each stack's `.env` mode 600, owned by the deploy user. The shared Caddy needs each
  stack's `GUI_PROXY_SECRET`: provisioning writes one site file per customer
  (`/etc/caddy/sites/<customer>.caddy`, mode 640, group of the Caddy container) that the main
  Caddyfile imports. Nothing of this is in the repository; the repository keeps templates with
  placeholders.
- **Never in logs, URLs or error answers:** the existing rule (docs/09 §5 checklist). Provisioning
  prints which variables it wrote, never their values. A setup link (§6) is shown once and stored
  hashed.
- **Rotation:** one runbook entry per token in docs/09 §2, written like "Kitchen token stolen or
  leaked". The dashboard offers "Token erneuern" per stack (step-up, audit), which writes the new
  value and restarts only the services that read it.
- **Offboarding (#576):** every token of the stack dies with the stack; the dashboard removes its
  `OPS_TOKEN` and the Caddy site file.

## 8. Read path from the dashboard to the stacks

The dashboard needs status and figures of every customer (#571) and, for support, sometimes one
guest's data.

**Chosen: an ops API in each stack's `api`, reached over an internal network per stack.**

- Each stack gets one more internal network, `ops`, with exactly two members: that stack's `api` and
  the operator dashboard. The dashboard joins every customer's `ops` network as an external network
  (provisioning adds it). Asterisk, n8n, `voice` and the database stay off it.
- Routes under `/v1/ops/*`, behind `OPS_TOKEN` (constant-time compare, refused at start when weak,
  distinct from every other token). Caddy answers 404 for `/v1/ops/*` on the customer's site, as it
  does for every path not on the public list today (`api/tests/test_deploy_exposure.py` keeps it so).
- **Default answers carry no personal data:** health, call mode, last call, counts of calls and
  orders today, print bridge heartbeat, backup age, open alerts, the four figures of docs/06 §4,
  menu status (items, price differences, missing allergens).
- **Personal data only with a reason:** a route that returns guest data (one call, one order, one
  customer record) requires `X-Ops-Reason` (a short category and a ticket or issue reference, no
  guest names) and `X-Ops-Actor`, and writes the customer's `audit_log` with actor
  `operator:<account>` and the reason before it answers. No bulk export over this API; an export is
  a data subject request (docs/09 §2) or offboarding (#576).
- **Writes** (settings, call mode, tokens) are separate routes, each writing `audit_log` with the
  operator as actor; changing the call mode or team number also pushes to the team (T12).
- The actor header is trusted only because only the dashboard holds `OPS_TOKEN`; the dashboard sets
  it from the session, never from user input.

Rejected:

| Option | Why not |
|---|---|
| The dashboard reads each database with a read-only role | the dashboard would hold every database's credentials and see every column; no reason recorded, no `audit_log` |
| The ops API on the public customer site | a new internet-facing path per customer for a server-to-server need |
| The dashboard joins each stack's `edge` network | `edge` also holds n8n, push and the dispatcher; more reach than the job needs |

**Shared Caddy:** the only container on several stacks' networks. It routes by host name only, each
site to its own stack's `api` with that stack's `GUI_PROXY_SECRET`. A test in the repo renders the
site template for two customers and fails when a site points at another stack's service name or
carries another stack's secret; provisioning runs the same check on the real site files after every
change.

## 9. Uploads (#572)

**D33 (Maxi 09.11.2026): no antivirus engine; files are sanitised instead.** ClamAV would cost about
1 to 1.5 GB of memory on the shared server and catches known malware only; the risk here is a parser
exploit, which sanitising in a sealed container addresses.

- **Who uploads:** the operator, in the dashboard (the customer sends pictures by whatever channel
  they use; that is outside the system).
- **Accepted:** JPEG, PNG and PDF, recognised by their first bytes, not by name or declared type.
  At most 20 MB per file, 40 files and 60 pages per customer intake. Everything else is refused with
  the reason.
- **Storage:** a private volume of the operator stack, one folder per intake, never under a path any
  web server serves, file names replaced by random ids.
- **Sanitising:** in a throwaway container per intake with no network, a read-only root, a non-root
  user, every capability dropped, limits of memory, CPU and time. It re-encodes each image (EXIF and
  other metadata dropped, a cap on pixels against decompression bombs) and rasterises each PDF page
  to an image; no PDF script, form or embedded file is ever run or kept. Only these copies go on to
  the extraction model and the review screen. The libraries for this (Pillow, a PDF rasteriser) go
  into that container's image only, not into `api`.
- **Never served raw:** the review screen shows the sanitised images from the dashboard with
  `Content-Disposition: inline`, the right image type and `nosniff`.
- **Deletion:** originals and copies are deleted when the import of that intake succeeds, and after
  14 days when an intake is abandoned. Where the extraction model sends data out of the server is a
  decision of its own in #572 (cost and data leaving, Maxi).

## 10. New libraries this design needs

| Library | For | Where |
|---|---|---|
| `webauthn` (py_webauthn) and what it pulls in | passkeys, operator dashboard | operator stack only |
| Pillow, a PDF rasteriser | sanitising uploads | the sanitiser image only |

Each goes into `requirements.in` with hashes (`make lock`) in the PR that first uses it. TOTP, scrypt
and tokens use the standard library.
